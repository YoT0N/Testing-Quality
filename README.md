# Testing-Quality

Виконав порівняння 4 різних варіацій програми:
 - v0 початковий код із репозиторію
    https://github.com/YoT0N/Testing-Quality/blob/main/src/Main.java
 - v1 початковий код з вимірюванням пам'яті 
    https://github.com/YoT0N/Testing-Quality/blob/with_memory_check/Main.java
 - v2 виправлений код із врахуванням "the"
    https://github.com/YoT0N/Testing-Quality/blob/finding_the/Main.java
 - v3 оптимізований код
    https://github.com/YoT0N/Testing-Quality/blob/optimized_code/src/Main.java

    До кожної варіації є відповідний скріншот, але різниця в часі виконання між оптимізованим кодом і неоптимізованим вийшла близько 1,5 секунди, тоді як різниця в пам'яті більше 180 МБ.
    Виконані пропозиції щодо оптимізації споживання ресурсу(пам'яті):
    1. Не тримаю весь файл у пам'яті. У v2 було Files.readAllBytes(...), тобто byte[] розміром з усю книгу. У v3 файл читається шматками по 16 КБ через InputStream.read(buf), один буфер на весь час роботи.
    2. Не створюю String з усього тексту. У v2 було new String(bytes), ще одна копія тексту. У v3 працюємо з сирими байтами, без декодування в символи.
    3. Не зберігаю int size = content.length(). Дрібниця, але це зайва змінна, яку ніхто не використовує.
    4. Фільтр символів без replaceAll. У v2 replaceAll("[^A-Za-z ]", " ") створює Pattern, Matcher і нову копію всього тексту. У v3 кожен байт перевіряється умовою b >= 'a' && b <= 'z і нічого не виділяється.
    5. Нижній регістр без toLowerCase. У v2 це була ще одна повна копія тексту. У v3 для великих літер просто b += 32.
    6. Без split(" +") і масиву words[]. У v2 кожне слово тексту ставало окремим String (заголовок об'єкта + внутрішній масив), і всі вони жили в пам'яті до кінця програми. У v3 окремі токени ніде не зберігаються.
    7. Без сортування Arrays.sort(words). Для нього треба тимчасового масиву під час сортування, а для підрахунку сортування не потрібне. 
    8. Один буфер для поточного слова. Замість нового об'єкта на кожне слово використовується один byte[] cur на 64 байти, який перевикористовується (і подвоюється лише для надзвичайно довгих слів).
    9. Хеш слова рахується під час читання (h = h * 31 + b), без окремого проходу по слову і без створення String для обчислення hashCode().
    10. Унікальні слова лежать в одному byte[] pool. У v2 для цього був рядок distinctString, який перевиділявся при кожному +=, і ще масив distincts після split. У v3 слово k це просто діапазон pool[start[k]..start[k+1]), кожне унікальне слово записане один раз.
    11. Прибрав конкатенацію рядків у циклі. distinctString += ... копіює весь накопичений рядок на кожній ітерації, тобто створює купу тимчасових великих String. У v3 замість цього System.arraycopy у готовий масив.
    12. Власна хеш-таблиця на int[] замість пошуку в рядку. У v2 пошук ішов через contains(" " + слово + " "), а це ще й нова String на кожну перевірку. У v3 таблиця з відкритою адресацією: 4 байти на комірку, без Node-об'єктів, які були б у HashMap.
    13. Масиви зростають лише за потреби. Початкові розміри підібрані під книгу, подвоєння через Arrays.copyOf відбувається тільки коли місця не вистачає, а таблиця перебудовується при заповненні більш ніж на 50%.
    14. Немає freq[] та distincts[i] += " " + freq[i]. У v2 для кожного унікального слова створювався новий String зі словом і числом. У v3 слово і лічильник зберігаються окремо (pool і count) і склеюються лише при друці.
    15. Прибрав регулярку в компараторі. У v2 кожне порівняння під час Arrays.sort(distincts, ...) викликало replaceAll("[^0-9]", "") та Integer.valueOf. Це найбільше сміття в програмі: на n·log n порівнянь по два тимчасових String і Integer. У v3 порівнюються готові числа.
    16. Відбір топ-30 замість сортування всіх. Замість сортування всього масиву унікальних слів у v3 підтримується int[30] з індексами найкращих слів, нове слово вставляється на своє місце, якщо воно краще за останнє. Додаткової пам'яті практично немає.
    17. Рядки створюються лише для 30 слів, які друкуємо. new String(pool, start, len, ISO_8859_1) викликається 30 разів, а не для кожного слова чи кожного унікального слова.
